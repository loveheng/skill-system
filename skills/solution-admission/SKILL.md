# solution-admission · 方案准入评估（补丁 vs 结构性引入）

> **定位**：动手**之前**的准入闸口——判定一个方案该以「结构性引入」还是「局部补丁」落地，并产出可追溯的发现（判定 + 理由 + 收敛条件）。补丁本身不是原罪，**隐形**的补丁才是：本 skill 的全部机制服务于「让债可见、可统计、可收敛」。
> **裁决链**：归 dev-loop（memory 决策 ＞ 项目 skill ＞ 通用规约）；本 skill 只给判定规则，被覆盖时无声让位。
> **豁免**：单文件微调 / 散修 / 纯咨询不过闸（对齐 dev-guide §0）。

**管辖边界（防越权）**：

| 事项 | 归属 |
|---|---|
| 大需求的**流程**怎么走（七步） | dev-guide §1 |
| 会话协议、日志、断点、验证账本 | dev-loop §2 |
| 权衡结论的**归档** | dev-loop §6 `::adr` → `decisions.md` |
| 待办类型、`[once]`/`[long]` 生命周期 | memo-collector §0 |
| 写码**之后**的不确定/降级/残留 | ai-sideeffect-guard §1/§2 |
| **准入判定 / 否决信号 / PATCH 标记 / 收敛阈值** | **本 skill** |

## 1. 三级分流与六条否决信号

开工前对改动做一次判定，落三档之一：

| 档 | 语义 | 处置 |
|---|---|---|
| **S1 局部修补** | 局部缺陷，结构没问题 | 放行，正常写码 |
| **S2 能力补丁** | 现有结构撑不住，缺的是**能力** | **否决**——回 §2 出结构性方案，禁止用补丁糊 |
| **S3 临时补丁** | 外部依赖未定 / 探索期 / 线上热修，权宜有正当理由 | 放行，但**必须**留 PATCH 标记（§4）+ 落风险待办（§3） |

**六条否决信号**（中任意一条即判 S2，逐条核对，禁止只看结论）：

| # | 信号 | 说明 |
|---|---|---|
| 1 | 需新增全局状态 / 跨模块传参才成立 | 数据归属错了 |
| 2 | 同样的处理要在第 2 个调用点再写一遍 | 缺的是能力，不是修一个点 |
| 3 | 出现 `if (旧行为) ... else ...` 的双路分支 | 系统里开始有两条路 |
| 4 | 被迫改公共数据结构 / 接口签名 | 影响面已超出局部 |
| 5 | 补丁体量接近原模块体量 | 这是没名分的重写 |
| 6 | 需要注释解释「这里为什么特殊」 | 特殊性是设计没做对的证据 |

> 第 2 条单独出现即可一票否决——重复是能力缺失最强的信号。

## 2. 评估三问（S2 判定后的必答项，各 ≤2 行）

1. **正确落点在哪一层**：先问正解，**禁止先考虑改动量**（"最小改动"是 AI 的默认偏好，不是评估过的结论）；
2. **影响面**：列出受影响的调用点（走 project-index L1/L2，禁止凭印象）；
3. **三次成本对比**：给 A 结构性方案 / B 补丁方案，分别写清「这个功能以后再改两次」各自的成本。

第 3 问是核心——它把"以后的成本"拉到当下，抵消 AI 天然只看当下的偏差。

## 3. 裁决与落盘（零新增容器）

| 产出 | 落点 | 时机 |
|---|---|---|
| 判定结论 + 否决理由 / 放行理由 | `decisions.md`（走 dev-loop §6 `::adr`，四段式） | 判定完当轮 |
| S3 临时补丁的收敛义务 | 待办台账 `(风险)` + `[long]`（落点路由 memo-collector §0） | 放行当轮 |
| 评估过程 | 绑定 epic 的 devlog（dev-loop §2） | 同上 |

`::adr` 条目必须写明**收敛条件**（"什么时候必须重构"），否则 S3 会退化为无限期债。

## 4. PATCH 标记约定

S3 放行时，在权宜实现处留一行注释（语言符号随语言）：

```
// PATCH: <为何权宜> | 正解: <应怎么做> | 重构条件: <何时必须改>
```

- **语义边界**（与 ai-sideeffect-guard §1 三者正交，禁止混用）：

| 标记 | 问题类型 | 语义 |
|---|---|---|
| `UNCERTAIN` | 认知 | 不知道对不对 |
| `DEGRADE` | 容错 | 失败了悄悄兜底 |
| `PATCH`（本 skill） | **取舍** | 知道不是正解，但先这样 |

- 有意的设计行为（如降级文案）不标 PATCH；标了就是**承认欠债**。
- 标记随代码生存，**不落 devlog**（对齐 ai-sideeffect-guard §1：标记不是日志）。
- 重构完成即删除标记——标记数只减不增是健康信号。

## 5. 收敛阈值与 ascan 工具

**阈值铁律**：同一位置第 3 次打补丁 → 强制重构（人记不住，交给机器）。

`admission-scan`（别名 `ascan`，toolbox 全局池，trigger: audit——`::audit` 自动跑，也可按需手动跑）：

```sh
toolbox run ascan --md /tmp/admission-report.md      # 明细报告（标记清单 + 补丁密度表）
toolbox run ascan --json                             # 单行契约结论（门禁消费）
toolbox run ascan --no-git                           # 快速：只扫标记，跳过密度统计
toolbox run ascan --threshold 3 --window 90          # 覆盖阈值与统计窗口
toolbox run ascan --self-test                        # 金丝雀自检
```

- **两件事**：扫 PATCH 标记（债清单）+ 统计命中文件的 git 提交次数（补丁密度，`--window` 默认 90 天）。
- **三态**：无债 exit 0；仅标记命中 exit 1 `warn`（债已登记，到期重评）；密度达阈值 exit 1 `error`（触发强制重构）。
- **白名单**：仓库根 `.admission-whitelist`（每行一个正则，仅收"经确认的有意权宜"）；**修复后必须删行恢复监控**——白名单 ≠ 已修复（对齐 ai-sideeffect-guard §3 口径）。
- 权威参数以脚本头部 `--help` 为 SSOT。

## 6. 反模式

- ❌ 把"最小改动"当选补丁的理由 → 那是默认偏好，不是论据；先答 §2 第 1 问
- ❌ S2 判成 S3 逃避重构 → "先这样以后再说"却无收敛条件 = 无限期债
- ❌ 临时补丁不留 PATCH 标记 → 债隐形，等价于没评估
- ❌ 只写判定结论、不逐条核对六条信号 → 走过场
- ❌ 重构后不删标记 / 不删白名单行 → 清单腐败，工具失去信号
- ❌ 小改动也过闸 → 散修豁免，流程成本不得压过收益
