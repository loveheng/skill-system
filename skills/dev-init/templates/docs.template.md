## 3. 操作纪律（正文机制指针 docs-spec，此处只列本项目动作）

- **新建**：frontmatter（`status` + `updated`）+ 同轮在 `docs/README.md` 加条目——**仅此一处**，不动本 skill、不动 `<index 数据路径>`。
- **移动/重命名**：按 `docs-spec §5` 同步 README 索引并**全仓 grep 精确文件名修引用**（含各 skill 与代码注释）。
- **废弃**：按 `docs-spec §4` 墓碑协议（翻 `status: deprecated` + 墓碑行），禁静默删除。
- **域级变迁（新增域/拆分/合并/整体迁移）**：按 `docs-spec §2` 三处同步——`docs/README.md` + `<index 数据路径>` 文档落点表 + 本 skill 域路由表。逐篇文档操作**不触发**本条。

**写后自检（AI 落笔三问，任一命中即删/移；判据正文 = `docs-spec §7` 反模式）**：

1. 这句是**现行事实**，还是**关于事实的历史**（何时新增/迁入/谁拍板）？——历史移交 devlog，正文删。
2. 是否写了「原没有 X」「此前缺失」「暂无 + 解释正常流程」类自证句？——删，只留结论。
3. 是否在复述另一事实源（文档数/文件清单/状态列）？——删，留指针指向唯一事实源（README / frontmatter / index）。

## 4. 文档评估方法论（依赖分级）

评估目的不是判断文档好坏，而是决定**依赖深度**。六维判据：

| 维度 | 判据 |
|---|---|
| D1 时效性 | frontmatter `updated`/`last-merge` 是否落后于代码实际变更；devlog 后续 `[变更]` 是否未回填 |
| D2 账实一致性 | 可机械定位断言（类名/路径/行号/阈值/开关）对代码实证，三态 ✅/❌/❓ |
| D3 单源状态 | 同主题有无矛盾表述（新旧并存）；指针能否 grep 定位 |
| D4 决策状态 | 结论「已拍板/待裁决/已废弃」是否显式；评估与实施是否分开陈述 |
| D5 验证账本 | 变更是否有成对 `[验证]`；「未执行」是否带原因+自证条件 |
| D6 信息密度 | 每条陈述是否携带可行动信息；有无遥测式重复 |

依赖分级（评估输出）：**L3 可直接依赖**（六维全过，作设计前提）｜**L2 抽查依赖**（关键断言动手前实证——读码纪律第③步）｜**L1 仅线索**（过期/缺验证/状态不明任一命中，一切以代码为准）。

使用时机：① 依赖前——文档建图时顺带分级（配套 `<repo>-workflow` 读码纪律，非额外动作）；② 变更后——触及断言同轮 SSOT 回填；③ 收尾时——`::audit` 机械项覆盖 D2/D3（::verify 三态、指针抽查），本方法论补 D1/D4/D5/D6 人判口径。
