# problem-triage · 排错协议 SSOT（八侧分流 + 接力循环 + 还原优先）

> **定位**：承载长排查/重大故障的完整协作协议正文（触发归 dev-loop 护栏 3，此处为协议 SSOT）；同时提供**八侧分类 + 各侧人类排查者背景**——分类是给人看的，人类入场排查前必须掌握对应侧背景。
> **裁决链**：归 dev-loop 护栏 3，本 skill 零裁决权。
> **人类侧说明书**：交接/还原/协作的人类视角指引 → 本目录 `manual.md`。

## 1. 八侧分类

| 侧 | 特征信号 | 典型例子 | 判断依据 |
|---|---|---|---|
| **代码侧** | 变更集相关；有报错或可复现 | 改错了；编译过但业务逻辑错；用了旧写法；修复引入新问题；隐性契约破坏 | `git diff <正常版本>..<故障快照>` 能对上 |
| **数据侧** | 代码无辜，**存量数据**是坏的 | 脏数据、迁移半途、schema 演进后旧记录不兼容、缓存过期格式 | 只在特定用户/特定老数据上触发；diff 查不出 |
| **环境侧** | 同一代码不同环境行为不同 | 依赖版本变了、上游接口变了、配置/开关漂移、本地无法复现 | 变更集无关 + 环境差异可指向 |
| **时序侧** | 不可复现/间歇性 | 竞态、缓存击穿、请求合并、顺序依赖 | 单测全绿、组合才错；需运行时证据 |
| **第三方侧** | 我方变更全无关，错误来自外部响应 | 上游风控封禁、Cookie/密钥/证书过期、配额用尽、对方悄悄改协议 | 集体突然失败；外部返回 403/429/封禁文案等 |
| **资源侧** | 与负载相关、渐进恶化、重启缓解 | OOM、磁盘满、连接池耗尽、QPS 超限 | 间歇性但随流量涨；监控曲线异常 |
| **发布侧** | 「跑的不是你以为的代码」 | 部署失败半截、灰度不一致、CDN/镜像缓存旧制品、回滚不完整 | 「本地是好的」；线上行为与同 commit 不符 |
| **意图侧** | 实现/测试/逻辑全对，用户说「不是我要的」 | 需求理解偏差 | 技术手段全部验不出，**只能问人** |

- 分流是**粗判不是结论**：多侧可并存，`[待验证假设]` 每条标主侧即可。
- **意图侧特殊**：一旦怀疑，**立即确认**（歧义阻断），严禁进入排查流程。

## 2. 各侧人类排查者需要的背景

| 侧 | 人类需要掌握的背景 | 常见来源 |
|---|---|---|
| 代码侧 | 最近变更的业务动机、改动评审上下文 | devlog、PR/commit 说明、用户口述 |
| 数据侧 | 生产/预发数据的访问途径、schema 版本历史、受影响用户/记录范围 | DB 访问权限、迁移记录、用户提供的查询结果 |
| 环境侧 | 各环境实际配置与依赖版本、部署时间线、监控/告警；**复杂环境操作可请人类协助直接执行**——AI 只给操作步骤与预期输出，不硬试不可达的环境 | 环境访问权限、监控平台、部署日志 |
| 时序侧 | 流量特征（高峰/QPS）、复现操作路径、运行时日志 | 生产日志（服务名+时间窗+关键标识）、用户操作复现步骤 |
| 第三方侧 | 上游平台状态、账号与配额面板、封禁/工单渠道 | 平台状态页、账号控制台、联系/工单记录 |
| 资源侧 | 监控指标（CPU/内存/磁盘/QPS 曲线）、容量告警与阈值 | 监控平台、容量告警记录 |
| 发布侧 | CI/CD 流水线状态、线上**实际**制品版本/commit、回滚记录 | 流水线平台、制品仓库、部署/回滚日志 |
| 意图侧 | 真实业务意图、验收标准、历史沟通上下文 | **只能问用户**，无替代来源 |

- **能自查的不外推**：AI 本地可达的来源（仓内配置、devlog、commit）先自查，查完仍缺才列入资源申请。

## 3. 排错协议（SSOT 正文）

### 3.1 交接单（三行 + 当前方案）

抛出后按接力循环续跑、**不阻塞等待**：

1. `[已排除]`：已证实不成立的假设（各附证据，防重复劳动）；
2. `[待验证假设]`：当前最可能的 1~3 个**错误方向**，各一行（假设 + 证实/证伪所需信息），尾部附侧别 `(代码侧|数据侧|环境侧|时序侧|意图侧|第三方侧|资源侧|发布侧)`；
3. `[需要用户]`：**具体资源申请清单**，优先「代执行」形态：**AI 给一条可直接粘贴的命令（只读探针优先）+ 预期输出说明，用户执行后原样回传**；需访问权/数据/决策的条目同样具体到位（日志：服务名+时间窗+关键标识；环境；查询）；严禁「帮我看看」式模糊请求；
4. `[当前方案]`（可选）：已有倾向方案时附——一句话结论 + 依据 + **置信度三档**（见 §3.4）。

### 3.2 接力循环（长排查的默认运行态）

长排查是 **AI 与人类交替接力的循环，直到解决验收**：

1. **节拍**：1 个节拍 = AI 自主跑一轮完整排查（推理 + 本地取证，含深度联读——联读对象在节拍末尾亮出即算进展输出）。**节拍是汇报周期的上限：节拍结束必抛交接单**（已解决则直接收尾）；
2. **停滞提前触发**：节拍内**连续 3 个推理/排查轮次未获得新信息**（新报错、新证据、新排除项）= 排查停滞 → **提前终止本节拍**、立即抛交接单（不必等节拍自然结束）；「轮」仅在节拍内计数，节拍切换后清零——抛单条件 = min(节拍结束， 停滞触发)；
3. **非阻塞接力**：交接单是**进展快照不是暂停键**——抛出后 AI 不等待，默认沿最高优先假设续跑下一节拍；人类回复随时合流：继续/补信息/否决（移入 `[已排除]` 重新收敛）/改方向/**重排假设优先级**（按业务权重，AI 遵从）——未回复即视为「按你的节奏继续」；
4. **挂起（仅用户可发起）**：任意响应中可附带挂起指令（「先停在这等我日志」「等我确认再继续，最多半小时」）——AI 挂起于当前节拍（进展已落 devlog 不丢），到期限或收到回复后继续，无期限则一直挂起（宁可等也不缺证据硬跑）；**AI 严禁自主挂起**；
5. **强制等待（唯一硬停）**：下一步是高危/不可逆操作（还原、生产变更）或 AI 即将执行大改动——必须拿到显式响应；
6. **防僵持**：同一主线假设连续 2 个节拍无新信息 → 下一节拍必须换侧别或换方向，严禁第三拍原题重跑；用户可随时「直接拍板」跳过节拍；
7. **退出**：仅两种——达成解决验收（§3.5）或用户明确叫停。AI 严禁单方面宣布「查不出」退出，也严禁连续多节拍不更新进展。

### 3.3 还原优先（五步，先推不先动）

触发熔断、或属**重大故障**（核心功能不可用 / 构建测试大面积红 / 数据或契约受损）时，提供「还原优先」选项，用户选定后按序走，全程严禁闷头排查：

1. **锚定正常版本**：用户口述「最后一次正常」为准；无口述时提议候选（devlog 最近 `[验证]` 通过的 commit > 最近手工 tag > `git log` 用户确认的时间点），**经用户确认才作数**；
2. **沙盘推演**：真实还原前 AI 先推演——revert 后哪些调用路径受影响、嫌疑 diff 最可能是哪几处、故障现象与推演是否吻合，给出「推演结论 + 嫌疑排序」；**推演已能锁定嫌疑范围时经用户确认跳过真实还原**，推演不收敛或用户要求实证时再走 3~4 步；
3. **快照现场**：还原前先固化当前故障态（`git stash` / 故障分支），保留排查证据，严禁直接丢弃；
4. **可逆还原**：只允许可回退手段（`git revert` / 从快照重建），**`reset --hard` / `clean -f` 等不可恢复操作默认禁用**（高危动作，需用户对具体命令显式授权）；还原后立即复测——故障消失则确认变更集嫌疑；
5. **变更复盘出方案**：`git diff <正常版本>..<故障快照>` 逐项核对与故障的相关性——**变更集相关** → 定位改动给修复方案；**变更集无关** → 排查转向环境/依赖/上游/时序/第三方/资源/发布，不在原改动上缠斗。复盘结论与方案**先反馈用户再动手**，确认后按 dev-loop §2 落盘（通用价值 Bug 记 Lesson）。

### 3.4 `[当前方案]` 置信度标尺（三档定性，绑定行为）

| 档 | 语义 | AI 的行为 |
|---|---|---|
| **高** | 证据链完整，方案有实证支撑 | 建议采纳，可请用户拍板收尾 |
| **中** | 证据支持但未闭环（缺一步验证/一个反例未排） | 请用户补充证据或否决，不建议直接拍板 |
| **低** | 仅方向合理，无实证 | 仅作方向参考，**严禁拿低置信度方案催拍板** |

跨节拍同名方案的置信度只升不降需附新证据；被新证据推翻则降档并回交接单。

### 3.5 解决验收（三样齐，严禁「不报错即收工」）

① 故障不可复现——**代码侧缺陷以先红后绿的最小复现用例（MRE）为硬证据**：修复前复现失败（红灯）、修复后通过（绿灯）；环境/数据/第三方/资源侧写不出单测，以探针/监控证据替代，**严禁硬造假测试**；② 相关回归面过一遍（防「修 A 坏 B」）+ **同模式扫描**——grep 同错误模式的兄弟代码点，命中列清单经确认处置（同轮修或转待办）；③ `[验证]` 账本行（dev-loop §2 口径）。业务逻辑错可零报错，故 ① 单独不成立。

**快照退场**：故障确认解决后，排查期快照（stash/故障分支）经用户确认处置——删除或转正式分支留档，不留孤儿快照。

### 3.6 跨会话落盘

长排查的交接清单（已排除 + 待验证假设，一行一条）在每次抛出时**同步追加到绑定 epic 的 devlog**（`- [YYYY-MM-DD] [排查交接]: ...`，计入归并阈值）——重置/新会话恢复按 dev-loop §3「排查交接例外」续上（恢复流 tail 扫 `[排查交接]` 行命中即续读），严禁从零重复排查。

### 3.7 根因排查纪律（代码侧 RCA，写死）

- **首次产生点锚定**：报错抛出点只是症状——沿数据流向上游追溯，锚定异常值/状态**最早偏离预期**的层级与行；严禁只按抛出点做局部修补。
- **假设-验证句式（写死）**：工作假设显式写成「推测 <X> 引起，因为在执行路径 <Y> 中状态 <Z> 发生 <偏离>」，并附证实/证伪所需信息——与交接单 `[待验证假设]` 行同口径（§3.1）。
- **最小侵入**：修复只动引发缺陷的必要逻辑，对齐工程既有命名/异步/错误处理惯例；影响面评估走 project-index 索引。「借修 Bug 顺手重构/优化」属越界——方案取舍归 solution-admission §1 三级分流（S1 局部修补 vs S2 结构性引入）。
- **红线指针**：表面掩盖（滥用可选链/空 catch/吞异常/无意义兜底值）归 ai-sideeffect-guard §1（标记约定 + 四工具机械收集，本节不复述口径）；未经确认引入新依赖归 dev-loop 护栏 5；契约保护归 dev-loop 护栏 6。

## 4. 边界

- 触发条件归 dev-loop 护栏 3（三维熔断）；本 skill 承载协议正文，日常小修、散修不加载。
- 不落长期容器——分类判断与交接单是易失工作产物，排查结论的持久化走 devlog/Lesson 既有通道。
